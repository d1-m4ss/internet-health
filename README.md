# Internet Health

Home internet monitoring in one Docker container: it checks your router, the internet and DNS around the clock, keeps the history per target,
explains outages in **readable messages** to Telegram (or Unraid), measures the speed with Fast.com, Cloudflare or Ookla on a schedule, and
shows it all on a dashboard with two styles and a Russian/English switch.

It runs on any always-on x86-64 machine with Docker — a mini PC, a NAS (Synology, QNAP, TrueNAS, OpenMediaVault, Unraid), a Proxmox VM or a
desktop with Docker Desktop. The image is `ghcr.io/d1-m4ss/internet-health`; you start it, open the web page and configure everything there.

> The screenshots show invented data (a fictional ASUS router at 192.168.1.1), generated by [`tests/demo_server.py`](tests/demo_server.py).

## Quick start

```sh
docker run -d --name InternetHealth --restart unless-stopped -p 8788:8080 -v ~/internet-health:/data \
  -e TZ=Europe/Berlin -e APP_TIMEZONE=Europe/Berlin -e ROUTER_IP=192.168.1.1 \
  -e SITES=fast.com,google.com,youtube.com,1.1.1.1,8.8.8.8 \
  ghcr.io/d1-m4ss/internet-health:latest
```

Open `http://<that machine>:8788`, then *Settings → Integrations* to get messages in Telegram. Full guide with docker compose, NAS GUIs, updating
and backups: **[docs/INSTALL.md](docs/INSTALL.md)**; Unraid (template and Unraid notifications): **[docs/INSTALL-UNRAID.md](docs/INSTALL-UNRAID.md)**.

## What you get

- **History per target and per measured IP** in SQLite: router, internet sites, DNS servers — loss, latency, jitter, DNS time. Nothing is
  deleted unless you choose a retention period.
- **Alerts that explain themselves.** Instead of `google.com: DOWN`, the message says what is wrong: *Router is not responding*,
  *No internet*, *Names do not resolve (DNS)*, *Unreachable: Google*, with icons, a hint what to check and, on recovery, how long the
  problem lasted. See [docs/NOTIFICATIONS.md](docs/NOTIFICATIONS.md).
- **No notification floods.** A change needs 2 consecutive bad samples; a steady outage sends one message, not one per probe; a target
  that keeps flapping is muted and summarised. 3 hours of flapping produce 5–6 messages instead of hundreds (see the simulator below).
- **Messages survive the outage.** They wait in a queue while the internet is down and are delivered when it is back, with a note how late
  they are.
- **Turbo mode (opt-in) for short outages.** A light watcher pings the router and two internet IPs every 5 s and reports outages from about
  10 s that the regular checks miss: one message after recovery with the duration, at most 3 per hour. Off by default.
- **Speedtest with three services, a schedule and a chart.** **Fast.com** (default) and **Cloudflare** are measured by Internet Health itself
  (no account, key or extra software); **Ookla** (Speedtest.net servers) uses Ookla's official CLI, which the first Ookla test downloads into
  the data folder — choosing it means accepting Ookla's terms (personal, non-commercial use). Every test records download, upload, latency,
  jitter and the latency under load (bufferbloat; Ookla also packet loss). Run tests by hand or off / every N hours / every day at set times,
  get a message after each, and a warning when the speed falls 20 / 30 / 50 % below the 7-day median of the same service. The chart shows
  speed, delay and loss on one time axis, with a button per line, one service or all of them (each with its own look), and a popup on hover.
- **A *WAN / ISP* card with your external IP, on request.** Off by default: nothing is requested and nothing recorded until you tick *Show my
  external IP and provider*; then the container asks `api.ipify.org` for the address and `ipwho.is` for the provider name when it changes —
  every 15 minutes, every minute, or only when you press *Refresh*.
- **WAN history and a WAN selector.** With that option on, every measurement is stored with the address and provider that carried it, so a
  failover to a backup link or a provider change can be told apart: a *WAN source* selector limits the chart, the *Targets* table and the
  *Packet loss* report to one source, the loss report compares the sources, and the compare chart can draw one line per source. An optional
  message tells you when the external IP or the provider changes.
- **Packet-loss report for any period** — summary, per-target table and a list of loss episodes; click an episode to zoom the chart onto it.
  Periods from 1 minute to a month, or a custom *from–to* window.
- **Compare mode** — several metrics and several targets (for example all DNS servers) on one chart.
- **Path to the internet:** server → router → Internet, drawn from the real targets, with the measured latency on the links.
- **Notifications where you want them.** *Settings → Integrations*: **Telegram** straight from the container (any machine), **Unraid**
  (email and every Unraid agent, through a small script on the Unraid host), both, or none — history and charts are recorded either way.
  The Telegram token is stored with mode 600 and never shown again.
- **Database backups and retention.** *Back up now* writes a consistent copy while monitoring keeps running (the 5 newest are kept, downloadable).
  *Keep history* for 7 / 30 / 90 / 180 days or 1 year deletes older records once a night; off by default.
- **Three UI styles (Classic, UniFi, Control), light / dark / auto theme, two languages**, a phone layout with a pinned one-row menu. One self-contained HTML page: no CDN,
  no external fonts, works offline on your LAN.
- **Careful by default.** It runs as an unprivileged user (99:100 unless you choose another), needs no Docker socket, no extra privileges and
  no host mounts besides its data folder. The only outbound requests are the probes, the Speedtest you run or schedule, the messages you
  configure and — only with the checkbox ticked — the public-IP lookup.

## How it works

```
 probe cycle (~50 s)           SQLite (/data)                    destinations (Settings → Integrations)
 ┌────────────────────┐   ┌────────────────────────────┐   ┌─────────────────────────────────────────┐
 │ Internet Health    │──▶│ measurements, targets,     │   │ Telegram: sent straight from the        │
 │ container          │   │ events, speedtests,        │──▶│ container (Bot API), queued offline     │
 │ (ping, DNS,        │   │ message queue …            │   ├─────────────────────────────────────────┤
 │  Speedtest)        │   │                            │   │ Unraid only: a host script (cron, 1 min)│
 └────────────────────┘   └────────────────────────────┘◀──│  GET /api/notifications/pending         │
        ▲ web page :8788      db-backups/ (copies)          │  → Unraid `notify` (mail + agents)      │
                                                            └─────────────────────────────────────────┘
```

More detail: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md); the HTTP API: [docs/API.md](docs/API.md).

## Requirements

- An always-on machine with Docker on the same network as the router (wired if possible), **x86-64 (amd64)** — ARM (Raspberry Pi, ARM NAS)
  is not supported yet.
- Nothing else for the page, the history, the Speedtest and Telegram. Unraid notifications additionally need the small script on the Unraid host.

The image is built from this repository's `Dockerfile` on `python:3.14-slim` pinned by digest, with every Python package pinned in
`requirements.txt`; Dependabot proposes newer versions weekly and CI builds and starts the image on every change.

## Updating

Releases are numbered ([semver](https://semver.org)) and published with notes on the [Releases page](https://github.com/d1-m4ss/internet-health/releases)
and in [CHANGELOG.md](CHANGELOG.md); the version is shown in the page footer and by `GET /api/about`. With compose: `docker compose pull && docker compose up -d`;
on Unraid: *Check for updates → Update*. The data folder is untouched and a new feature stays off until you switch it on. Use a tag such as `:1.4.0`
to stay on one version. Details: [docs/INSTALL.md → Updating](docs/INSTALL.md#updating).

## Configuration

| Variable (container) | Meaning |
|---|---|
| `ROUTER_IP` | router address; becomes the *Router* node and the first thing blamed when it does not answer |
| `ROUTER_NAME` | label used in the page and in messages (default `Router`, e.g. `ASUS RT-AX86U`) |
| `SITES` | comma-separated ping targets; include 1–2 IP addresses besides names (default `fast.com,google.com,youtube.com`) |
| `DNS_NAMESERVER_n` / `_IP` | DNS servers checked, `n` = 1–4 (default Google, Quad9, Cloudflare) |
| `DNS_TEST_SITES` | names resolved at each DNS server (default `google.com`) |
| `PROBE_INTERVAL`, `PING_COUNT`, `PING_WAIT` | pause between probe cycles (default 30 s), pings per target (4), seconds to wait for the last reply of a ping (2) |
| `SPEEDTEST_ENABLED`, `SPEEDTEST_INTERVAL`, `SPEEDTEST_BACKEND` | scheduled tests, their interval in seconds and the service (`fast`, the default, `cloudflare` or `ookla`); the *Speedtest* tab overrides service and schedule |
| `TZ`, `APP_TIMEZONE` | time zone of the container and of the daily Speedtest times (default `UTC`) |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | optional: Telegram without the form in the page (both needed; they win over the saved values) |
| `PUID`, `PGID` | the user the app runs as (default `99` and `100`); the container starts as root only to hand the data folder to it, then drops the privileges. `PUID=0` runs as root |
| `WEIGHT_*`, `THRESHOLD_*` | weights and limits of the 0–100 quality score |
| `GUNICORN_CMD_ARGS` | already `--threads 4`; never raise `--workers`: every worker would start its own probe loop |

Alert thresholds (loss ≥ 10 %, RTT ≥ 150 ms, jitter ≥ 80 ms, DNS ≥ 250 ms, 2 samples to alert, 2 to recover) are edited in the page
(*Notification thresholds*) or in `/data/alert-settings.json`.

## Try it, test it, break it — without sending anything

```sh
python -m venv .venv && . .venv/bin/activate && pip install -r requirements.txt
python -m unittest discover -s tests          # unit + integration tests (real Flask app, real bridge script, fake services)
python tests/simulate_network.py -v           # real probe loop + queue + bridge on a virtual clock, fake ping/DNS
npm install && npx playwright install chromium && node tests/test_ui.cjs   # browser tests, both styles/languages
node tests/test_mobile_nav.cjs && node tests/test_speedtest_ui.cjs          # pinned menu on phones; Speedtest, schedule, public IP
```

The simulator runs 20 failure scenarios (outage, DNS-only outage, router down, flapping, restarts, a dead notifier, …) through the real code;
**no real message or network request is made**. `CHROME_PATH=/path/to/chrome` makes the browser tests use an installed browser.

To look at the dashboard without a real network, run `python tests/demo_server.py` and open <http://127.0.0.1:8799> (add `--failing` to end with
an outage). It runs the real app on invented data; `node tests/screenshots.cjs` regenerates the pictures in `docs/screenshots`.

## Security notes

- The web page and API have **no authentication**. Keep port 8788 on your LAN; never expose it. Anyone who can open the page can change the
  settings (including Telegram) and download the database backups.
- The settings endpoints accept only same-origin browser requests with an `X-NetProbe-Request` header (the header keeps its original name).
- The Unraid message queue is private to the host: `X-NetProbe-Notify-Key` (a random 256-bit token created on first start in
  `/data/notify-token`, mode 600) is required to read or acknowledge it.
- Do not publish the data folder (database, token, settings) anywhere; see `.gitignore`.

## Limitations

- Probes are sequential: a cycle takes about 50 s when everything answers and about 100 s during an outage. A change must be seen in **two
  consecutive cycles**, so an outage shorter than about 1.5 minutes is never reported by the regular checks and one of about 2.5 minutes always
  is. **Turbo mode** (off by default) catches outages from about 10 s; it costs about 9 MB of ICMP per day, and an ISP that rate-limits ICMP to
  *all* internet targets at once can cause a false report.
- **Fast.com** and **Cloudflare** numbers come from Internet Health's own client (latency, then 8 connections for 8 s down and 4 for 8 s up);
  they can differ from the services' web pages, so compare a service with itself over time. A test uses real bandwidth for about 20 s.
- Fast.com and Cloudflare publish no API guarantee for the endpoints their pages use; if one changes them, that service fails with a readable
  message and the others keep working. Ookla's CLI is version 1.2.0 for Linux; its terms are Ookla's.
- If the whole network is down, nothing can leave it until it is back (messages are queued); an external watcher is needed to learn about a
  full-site outage while it lasts.
